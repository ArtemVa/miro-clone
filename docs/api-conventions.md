# Соглашения API

## Адреса

- Все эндпоинты начинаются с `/api`. По этому префиксу сервер отличает запросы к api от страниц фронта.
- Ресурс называем существительным во множественном числе, через дефис: `/api/users`, `/api/order-items`.
- Вложенность — не глубже одного уровня: `/api/users/:id/orders`.
- Действие, которое не сводится к созданию, чтению, изменению или удалению, — отдельный `POST`: `POST /api/orders/:id/cancel`.

Версию в адрес (`/api/v1`) не добавляем. Совместимость держим правилами из [contracts-and-review.md](contracts-and-review.md#как-менять-существующий-контракт).

## Данные

- Поля JSON — в camelCase: `createdAt`, `pageSize`.
- id — uuid строкой.
- Даты — строки ISO 8601 в UTC: `2026-11-08T10:00:00.000Z`, в contracts — `z.iso.datetime()`. В местное время переводит фронт.

## Ошибки

Любая ошибка приходит в одном формате — `ApiErrorSchema` из contracts:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Request body does not match the contract",
  "issues": [{ "path": "email", "message": "Invalid email address" }]
}
```

- `code` — значение из `ErrorCodeSchema`. Фронт решает, что делать, по `code`, а не по тексту `message`.
- `message` — текст для человека, может меняться.
- `issues` — только у `VALIDATION_ERROR`: какое поле не прошло проверку и почему.

Если id в адресе не uuid (`/api/users/abc`), ответ — 400 `VALIDATION_ERROR`, а не 404: такой записи не может быть, ошибка в самом запросе. 404 — когда id правильный, но записи с ним нет.

| Статус | `code`             | Когда                                                  |
| ------ | ------------------ | ------------------------------------------------------ |
| 400    | `VALIDATION_ERROR` | тело или параметры запроса не прошли проверку схемой   |
| 400    | `BAD_REQUEST`      | запрос не удалось разобрать, например битый JSON       |
| 404    | `NOT_FOUND`        | нет такой записи или такого адреса                     |
| 409    | `CONFLICT`         | конфликт с существующими данными, например email занят |
| 500    | `INTERNAL_ERROR`   | ошибка на сервере                                      |

Новый код ошибки — это новое значение в enum, который приходит в ответе. Добавляем его по шагам, как написано в [contracts-and-review.md](contracts-and-review.md#как-менять-существующий-контракт).

## Списки

Любой эндпоинт, который отдаёт список, отдаёт его по страницам.

```
GET /api/users?page=2&pageSize=20
```

- `page` — номер страницы, начиная с 1. По умолчанию 1.
- `pageSize` — записей на странице. По умолчанию 20, максимум 100.

Ответ:

```json
{
  "items": [{ "id": "…", "name": "Ivan" }],
  "total": 57,
  "page": 2,
  "pageSize": 20
}
```

`total` — сколько записей всего. Страница за концом списка возвращает пустой `items`, а не 404.

### Сортировка

```
GET /api/users?sort=name&order=asc
```

- `sort` — поле, по которому сортируем. Допустимые поля перечислены в схеме параметров списка: у пользователей это `createdAt` и `name`.
- `order` — `asc` или `desc`.

У каждого списка свой порядок по умолчанию, обычно `createdAt` и `desc`: сначала новые. Если `order` не передан, он тоже берётся по умолчанию: `?sort=name` у пользователей отсортирует имена по убыванию.

### Фильтры

```
GET /api/orders?status=active&search=ivan&createdFrom=2026-01-01T00:00:00.000Z
```

- Фильтр — обычный query-параметр с именем поля: `status=active`.
- Поиск по тексту — параметр `search`.
- Диапазон — `<поле>From` и `<поле>To`: `createdFrom`, `createdTo`.

Какие фильтры есть у списка, описывает схема его параметров в contracts.

### На бэке

Пагинацию, сортировку и фильтры делает база, через ORM: `WHERE`, `ORDER BY`, `LIMIT` и `OFFSET` в запросе, `total` — через `COUNT` с тем же `WHERE`. Выбирать все записи и фильтровать, сортировать или резать их в коде нельзя.

К выбранному полю сортировки бэк всегда добавляет последним уникальное поле (обычно `id`). Иначе записи с одинаковым значением перескакивают между страницами: одна повторяется, другая пропадает.

### Схемы в contracts

Параметры списка — общая схема пагинации, расширенная сортировкой и фильтрами. Ответ — `paginated()`:

```ts
export const UserListQuerySchema = PaginationQuerySchema.extend({
  sort: z.enum(['createdAt', 'name']).default('createdAt'),
  order: SortOrderSchema.default('desc'),
});

export const UserListSchema = paginated(UserSchema);
```

Если параметры списка неверные, ответ — 400 с кодом `VALIDATION_ERROR`.

Пример — `GET /api/users` в `apps/api/src/modules/users`.

## Id запроса

Каждый ответ приходит с заголовком `X-Request-Id`. Если показать этот id в сообщении об ошибке, бэк по нему найдёт запрос в логах.

Фронт может прислать свой `X-Request-Id`. Бэк возьмёт его, если это до 100 символов из латинских букв, цифр, `_` и `-`, иначе сгенерирует новый.
