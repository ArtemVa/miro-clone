# Ветки, коммиты и PR

## Ветки

- `dev` — рабочая ветка, все задачи мержатся сюда.
- `main` — в неё попадает только `dev`, через PR.
- Задачу делаем в отдельной ветке от `dev`. В имени — тип и номер задачи: `feat/123-user-registration`, `fix/130-login-error`.

Когда появится dev-окружение, мерж в `dev` будет автоматически выкатываться на него.

## Коммиты

Формат — [Conventional Commits](https://www.conventionalcommits.org/ru/). Хук `commit-msg` проверяет его при каждом коммите.

```
<тип>(<область>): <что сделано>
```

Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. Область указывать необязательно: `api`, `contracts`, `web`.

```
feat(api): add user registration
fix(contracts): make phone optional
```

Коммиты пишем на английском, кириллицу хук не пропустит. Описание начинаем с маленькой буквы, точку в конце не ставим.

## Перед коммитом

Хук `pre-commit` запускается на файлах, добавленных в коммит:

- `.ts` — проверка типов, ESLint с автоисправлением, Prettier;
- остальные (`json`, `md`, `yml` и т.д.) — Prettier.

Если хук упал, коммит не создаётся. Исправляем ошибки и коммитим снова. Хуки ставятся сами при `pnpm install`.

## PR

1. Открываем PR из своей ветки в `dev`.
2. Кидаем ссылку в чат по PR. Мержим только после того, как PR согласовали в чате.
3. Если PR меняет `packages/contracts`, его согласуют и бэк, и фронт. Подробнее — в [contracts-and-review.md](contracts-and-review.md).
4. CI проверяет форматирование и запускает lint, typecheck, test и build для пакетов, которые затронул PR. С красным CI не мержим. GitHub этого не запрещает, это наша договорённость.
5. Мержим обычным merge commit (Create a merge commit), без squash и rebase.

Релиз — PR из `dev` в `main`.
