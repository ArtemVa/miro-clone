# Ветки, коммиты и PR

## Ветки

- `dev` — рабочая ветка, все задачи мержатся сюда. Когда появится dev-сервер, мерж в `dev` будет автоматически выкатываться на него.
- `main` — прод. В неё попадают только релизные ветки `release/x.y.z`, через PR.
- Задачу делаем в отдельной ветке от `dev`. В имени — тип, номер задачи из YouGile и пара слов по-английски: `feat/PRO-12-board-crud`, `fix/PRO-30-login-error`.

В `dev` и `main` нельзя пушить напрямую, делать force push и удалять их. GitHub это запрещает всем, включая админов.

## Коммиты

Формат — [Conventional Commits](https://www.conventionalcommits.org/ru/). Хук `commit-msg` проверяет его при каждом коммите.

```
<тип>(<область>): <что сделано>
```

Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. Область указывать необязательно: `api`, `contracts`, `web`.

```
feat(api): add user registration
fix(contracts): make phone optional
```

Коммиты пишем на английском, кириллицу хук не пропустит. Описание начинаем с маленькой буквы, точку в конце не ставим.

## Перед коммитом

Хук `pre-commit` запускается на файлах, добавленных в коммит:

- `.ts` — проверка типов, ESLint с автоисправлением, Prettier;
- остальные (`json`, `md`, `yml` и т.д.) — Prettier.

Если хук упал, коммит не создаётся. Исправляем ошибки и коммитим снова. Хуки ставятся сами при `pnpm install`.

## PR

1. Открываем PR из своей ветки в `dev`. В заголовке — номер задачи, например `PRO-12`.
2. Кидаем ссылку в чат по PR.
3. Мержим после approve в GitHub. Approve ставит не автор PR и не тот, кто последним пушил в его ветку.
4. Новый коммит в PR сбрасывает approve, нужен новый.
5. Все обсуждения в PR должны быть закрыты (Resolve conversation).
6. CI проверяет форматирование и запускает lint, typecheck, test и build для пакетов, которые затронул PR. С красным CI смержить нельзя.
7. Мержим обычным merge commit (Create a merge commit), squash и rebase отключены.

Пункты 3–7 проверяет GitHub: пока они не выполнены, смержить PR нельзя.

Если PR меняет `packages/contracts`, нужен approve и от бэка, и от фронта. GitHub этого не проверяет, это наша договорённость. Подробнее — в [contracts-and-review.md](contracts-and-review.md).

## Релиз

1. От `dev` создаём ветку `release/x.y.z`.
2. Открываем PR из неё в `main`. Для него действуют те же правила, что и для PR в `dev`.
3. После мержа публикуем GitHub Release с тегом версии. Когда настроим деплой, публикация Release будет выкатывать прод.

Исправление к релизу сначала делаем обычным PR в `dev`, потом переносим в релизную ветку через `git cherry-pick`.

Что в `main` попадают только ветки `release/*`, GitHub пока не проверяет. Эта проверка появится в CI.
