# Контракты и ревью

`packages/contracts` — общие zod-схемы фронта и бэка. По ним бэк проверяет входящие запросы и типизирует ответы, а фронт типизирует запросы и проверяет формы. Контракт — договорённость двух команд, поэтому одна сторона не меняет его без другой.

## Что кладём в contracts

Кладём то, с чем работают и фронт, и бэк:

- схемы тел запросов и ответов;
- enum'ы и коды ошибок, которые получает фронт;
- типы, выведенные из схем через `z.infer`.

Не кладём:

- модели и типы БД;
- то, что нужно только одной стороне;
- код, которому нужно что-то кроме `zod`: Node API, Express, React.

Контракт описывает данные так, как они идут по сети, а не так, как лежат в базе. Дата в контракте — строка (`z.iso.datetime()`), потому что в JSON нет дат. Поля вроде `passwordHash` в контракт не попадают. Модель БД в формат контракта переводит бэк.

## Как оформляем

- Один файл на предметную область (`users.ts`, `orders.ts`), всё экспортируется через `src/index.ts`.
- Схема называется с суффиксом `Schema`, выведенный тип — тем же именем без суффикса:

  ```ts
  export const UserSchema = z.object({/* ... */});
  export type User = z.infer<typeof UserSchema>;
  ```

- Тело запроса называем по действию: `CreateUserBodySchema`, `UpdateUserBodySchema`.

## Новая фича: сначала контракт

Если фича задевает и фронт, и бэк, начинаем с контракта, а не с кода.

1. Бэкендер, который взял фичу, открывает PR только с изменениями в `packages/contracts`. В описании пишет метод и путь эндпоинта, что приходит в запросе, что уходит в ответе и какие бывают ошибки.
2. Фронт и бэк обсуждают схемы, approve ставят обе команды. Мержить его безопасно: новые схемы пока никто не использует.
3. Дальше работаем параллельно. Бэк делает эндпоинт, фронт делает интерфейс на моках по тем же схемам.
4. Фронт выкатывает вызов нового эндпоинта только после того, как бэк выкатил сам эндпоинт.

## Ревью

PR мержим после approve в GitHub (общий порядок — в [git-and-pr.md](git-and-pr.md)). Кто ставит approve, зависит от изменённых файлов:

- `apps/api` — бэк;
- `apps/web` — фронт;
- `packages/contracts` — и бэк, и фронт, минимум по одному человеку от каждой команды.

Если PR меняет contracts, автор отмечает в чате другую команду. Пока нет approve от обеих команд, PR не мержим. GitHub требует только один approve, второй — наша договорённость.

На ревью отправляем PR, когда он готов целиком. Если после approve в PR появились новые коммиты (например, фронт дописал свою часть в общий PR), GitHub сбрасывает approve, и PR одобряют заново.

## Как менять существующий контракт

Даже если фронт и бэк выкатываются одним деплоем, у пользователей могут часами висеть открытые вкладки со старой версией фронта. Они продолжают слать запросы в старом формате уже на новый бэк. Поэтому бэк всегда должен принимать запросы и от старого фронта, и от нового.

За один PR можно:

- добавить поле в ответ;
- добавить необязательное поле в запрос;
- добавить новый эндпоинт.

Только по шагам:

- сделать поле обязательным;
- переименовать или удалить поле;
- поменять тип поля;
- добавить значение в enum, который приходит в ответе: фронт, который проверяет ответ через `z.enum`, упадёт на незнакомом значении.

Пример: при регистрации нужно обязательно передавать `phone`.

1. PR бэка: в `CreateUserBodySchema` добавляем `phone: z.string().optional()`, бэк сохраняет поле. Старый фронт работает как раньше.
2. PR фронта: форма регистрации отправляет `phone`.
3. PR бэка: убираем `.optional()`. Не в день выкатки фронта, а позже: старые вкладки ещё какое-то время шлют запросы без `phone`.

Переименование и удаление делаются так же: добавляем новое поле рядом со старым, переводим фронт на новое, удаляем старое.

## Один PR или два

Если изменение контракта совместимое, бэк мержит свой PR сам, после согласования с фронтом. Фронт подхватывает изменение своим PR, когда до него дойдёт.

Общий PR двух команд делаем, только если фича маленькая и обе стороны готовы прямо сейчас: такие PR долго висят и обрастают конфликтами. Правила совместимости действуют и для общего PR: после выкатки старые вкладки фронта никуда не деваются.
