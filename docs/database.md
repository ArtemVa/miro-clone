# База данных

Postgres 18 в Docker (`docker-compose.yml` в корне), ORM — Prisma 7. Миграции и сиды пишут бэкенд-разработчики.

## Где что лежит

- `apps/api/prisma/schema.prisma` — схема.
- `apps/api/prisma/migrations/` — миграции, лежат в git.
- `apps/api/prisma/seed.ts` — сиды.
- `apps/api/src/common/db.ts` — создание клиента Prisma.
- `apps/api/src/common/db-errors.ts` — ошибки базы, которые репозитории отдают сервисам вместо ошибок Prisma.
- `apps/api/src/modules/<модуль>/<модуль>.repository.ts` — запросы к базе. Кроме репозиториев, запросов к базе в модулях нет, см. [backend-structure.md](backend-structure.md).
- `apps/api/src/generated/prisma/` — сам клиент. Генерируется из схемы и в git не попадает. Turbo пересоздаёт его перед `dev`, `typecheck`, `lint`, `test` и `build`.

## Команды

```sh
pnpm db:migrate --name add-orders   # создать миграцию из изменений схемы и применить к локальной базе
pnpm db:seed                        # залить тестовые данные; повторный запуск ничего не дублирует
pnpm db:deploy                      # применить миграции, не создавая новых, — так делает сервер
pnpm db:generate                    # пересоздать клиент Prisma, если редактор не видит новых полей
```

## Миграции в Docker

В контейнерах миграции применяет одноразовый сервис `migrate` (профиль `app` в `docker-compose.yml`). Он собирается из стадии `migrate` в `apps/api/Dockerfile`, где стоят все зависимости, включая Prisma CLI, и запускает `pnpm db:deploy`. Сервис `api` стартует только после того, как `migrate` завершился без ошибок. Поэтому `prisma` остаётся в devDependencies.

## Как менять схему

1. Меняем `schema.prisma`.
2. Запускаем `pnpm db:migrate --name <что поменяли>`. Prisma создаст папку миграции с SQL, применит её к локальной базе и пересоздаст клиент.
3. Проверяем SQL в созданной миграции и коммитим его вместе со схемой.

Миграцию, которая уже попала в `dev`, не редактируем: она выполнена у других и на сервере. Ошибку исправляем новой миграцией.

## Соглашения

- Таблицы называем в snake_case во множественном числе, колонки — в snake_case: `@@map("users")`, `@map("created_at")`. В коде поля остаются в camelCase.
- id — uuid v7: `@id @default(dbgenerated("uuidv7()")) @db.Uuid`. Значение генерирует база функцией `uuidv7()` из Postgres 18, поэтому id получит и запись, вставленная не через Prisma. Такие uuid растут со временем, поэтому вставки не разбрасываются по индексу.
- Даты — `@db.Timestamptz(3)`, время с часовым поясом.
- Строку из базы переводим в формат контракта в сервисе (даты — через `toISOString()`). Типы Prisma наружу из сервиса не отдаём.

## Ограничения в базе

Уникальность, обязательность и связи держит база: `@unique`, поля без `?` (`NOT NULL`), внешние ключи через `@relation`. Проверка в коде их не заменяет: два одновременных запроса пройдут её оба.

Нарушение ограничения бэк переводит в ошибку API. Например, нарушение уникальности (код Prisma `P2002`) репозиторий превращает в `UniqueViolationError`, а сервис — в 409 `CONFLICT`. См. `create` в `users.repository.ts` и `users.service.ts` в `apps/api/src/modules/users/`.

Схемы zod проверяют запрос до похода в базу и отвечают понятной 400. Ограничения в базе — вторая линия: они держат данные целыми, даже если в коде ошибка.

## Тесты

Тесты api работают с настоящей базой `app_test` в том же Postgres, поэтому перед `pnpm test` нужен `docker compose up -d`.

- Перед запуском к `app_test` применяются миграции. Если базы нет, Prisma её создаст.
- Перед каждым тестом все таблицы очищаются. Очистка откажется работать с базой, имя которой не кончается на `_test`.
- Данные для теста создаём через API или прямо через Prisma, если нужно задать поля, которых нет в контракте (например, `createdAt`).
- Файлы тестов выполняются по очереди: база одна на всех.

В CI Postgres поднимается сервисом в `.github/workflows/ci.yml`.
